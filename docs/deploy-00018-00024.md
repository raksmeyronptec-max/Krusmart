# Deploying migrations 00018 – 00024

Seven migrations have been verified locally and have **never run on the live
project**. This is the order to apply them in, what to check before and after
each one, and how to undo it.

Written to be followed by one person, alone, possibly tired. Every step is
copy‑paste. Nothing here requires judgement except where it says so in bold.

---

## Before you start

**1. Take a backup.** Supabase dashboard → Database → Backups. Do not skip
this. Everything below is reversible in principle; a backup is what makes it
reversible in practice.

**2. Look at the live schema first.** Run
[`supabase/audits/schema_snapshot.sql`](../supabase/audits/schema_snapshot.sql)
in the SQL editor and compare it against the committed baseline in the same
directory. Migration 00017's header exists because a dependency nobody
predicted from reading SQL — `schools_select_member` reading `profiles.school_id`
rather than `user_roles.school_id` — was found by inspecting a live database.
**Assume one more surprise is waiting.** If section 7 shows anything from
00001–00017 as `absent`, stop and work out why before going further.

**3. Confirm where live actually is.** Section 7 of that same file reports each
of 00018–00024 as `present` or `absent`. All seven should read `absent`. If any
reads `present`, that migration was applied by hand at some point — skip it, and
run its verification query to confirm it landed completely.

**4. Nothing is deployed yet.** The app is local‑only today, so no running code
depends on any of these functions. That is what makes this window safe: you can
apply, verify and roll back freely. See *Point of no return* at the foot for
what changes the day you first deploy.

**5. Confirm the Postgres version is 15 or newer.**
```sql
SELECT current_setting('server_version_num')::int >= 150000 AS ok, version();
```
**00021 requires PostgreSQL 15 or newer.** Its unique index uses
`NULLS NOT DISTINCT`, which does not exist before 15 — on 14 or older the
statement is a syntax error and the whole migration aborts.

Run that query **against live**, not against a local Docker stack. Local
Supabase pulls a current Postgres image; a live project created years ago can
sit several majors behind it, so the local version tells you nothing about the
one that matters. If 00016 applied cleanly to live then live is already 15+,
because 00016 uses the same syntax — but confirm it rather than reason about
it.

**How to copy a migration.** Open the file under `supabase/migrations/`, paste
the executable SQL into the editor, run.

- **00020 – 00024** are wrapped: select from `BEGIN;` through `COMMIT;`
  inclusive. Everything below `COMMIT;` is commented notes — do not paste it.
- **00018 and 00019** have **no** `BEGIN;`/`COMMIT;` — each is a single
  `CREATE OR REPLACE FUNCTION` followed by its `COMMENT`, `REVOKE` and `GRANT`.
  Select from the first `CREATE OR REPLACE FUNCTION` down to the last `GRANT`
  line, and stop before the commented `VERIFICATION` block. A single function
  replacement is atomic on its own; the grants that follow are not, so if the
  editor reports an error partway, re-run the whole selection — it is
  idempotent.

## Order

Apply in numeric order. Two hard dependencies:

- **00019 must follow 00018.** 00019 redefines the function 00018 creates. If
  you apply 00019 to a database without 00018, you get 00019's function anyway
  (it is `CREATE OR REPLACE`), which is *correct* but leaves the numbering
  lying about history. If you ever apply 00018 **after** 00019 you silently
  reintroduce the cross‑year promotion bug. Never go backwards.
- **00021 must follow 00016.** It alters `score_template_subjects` and replaces
  the unique index 00016 created.

The rest are independent of each other and could be applied in any order; do
them in sequence anyway, so the preflight/verify rhythm stays simple.

---

## 00018 — roster recovery function

**What** Creates `backfill_teacher_enrolments()`, which enrols a teacher's
`students.teacher_id` roster into their active homeroom class.

**Preflight** — expect `absent`:
```sql
SELECT CASE WHEN to_regprocedure('public.backfill_teacher_enrolments(uuid)') IS NULL
            THEN 'absent — apply it' ELSE 'present — skip' END AS verdict;
```

**Apply** `supabase/migrations/00018_backfill_teacher_enrolments.sql`.

**Verify** — expect one row, `SECURITY DEFINER`, with a pinned `search_path`:
```sql
SELECT p.proname,
       CASE WHEN p.prosecdef THEN 'SECURITY DEFINER' ELSE 'invoker' END AS security,
       array_to_string(p.proconfig, ', ') AS config
  FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
 WHERE n.nspname = 'public' AND p.proname = 'backfill_teacher_enrolments';
```

**Rollback** `DROP FUNCTION IF EXISTS public.backfill_teacher_enrolments(UUID);`
Enrolment rows it created are ordinary rows and are left in place — see the
file's own ROLLBACK note for removing them per class.

**Still safe after the next one?** No — 00019 replaces this function. Dropping
it after 00019 removes 00019's version too. Roll back 00019 first, or accept
that both go.

## 00019 — enrol only never‑enrolled students

**What** Redefines 00018's function so it enrols only students with **no**
enrolment row at all. 00018's year‑scoped guard silently promoted last year's
roster into a new class; this is the fix.

**Preflight** — 00019 replaces a function body and creates no object, so
presence has to be read out of `prosrc`. The body carries a declared marker
line for exactly this purpose:
```sql
SELECT CASE
         WHEN prosrc LIKE '%version-marker: backfill-never-enrolled-only%'
           THEN 'present — skip'
         ELSE '00018 only — apply 00019'
       END AS verdict
  FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
 WHERE n.nspname = 'public' AND p.proname = 'backfill_teacher_enrolments';
```
No rows → 00018 has not been applied. Go back one step.

Do not be tempted to discriminate on anything else in the body. An earlier
version of this runbook tested for `academic_year`, which 00019 still writes —
so it matched both versions and reported "apply 00019" forever. The marker
comment in 00019 is load-bearing; do not edit it.

**Apply** `supabase/migrations/00019_backfill_never_enrolled_only.sql`.

**Verify** — the preflight above should now read `present — skip`. Then confirm
the behaviour actually changed, which is the point of the migration: the body
must no longer skip a teacher merely because they have an enrolment in the
target year.
```sql
SELECT
  (prosrc LIKE '%version-marker: backfill-never-enrolled-only%') AS marker_present,
  (prosrc LIKE '%NOT EXISTS%')                                   AS enrols_never_enrolled_only,
  prosecdef                                                      AS security_definer,
  array_to_string(proconfig, ', ')                               AS search_path
  FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
 WHERE n.nspname = 'public' AND p.proname = 'backfill_teacher_enrolments';
-- expect: t | t | t | search_path=public, pg_temp
```

**Rollback** Re‑apply 00018's `CREATE OR REPLACE FUNCTION` block. **This
reintroduces a known bug** — only do it if 00019 is somehow causing worse.

**Still safe after the next one?** Yes. Nothing later touches this function.

## 00020 — extended teacher profile

**What** Adds a `teacher_profiles` table and two `settings` columns for

**Preflight** — expect `absent`:
```sql

**Verify** — expect the table plus four policies:

         WHERE table_schema='public' AND table_name='settings'

```

**Rollback** In the file. Fully reversible; nothing else reads these.

**Still safe after the next one?** Yes. Independent of everything below.

## 00021 — level, grade and track on the score template

**What** Adds `level_key` / `grade_number` / `track` to
`score_template_subjects` and `track` to `classes`; replaces the unique index;
seeds the twelve verified Grade‑12 subject rows (both streams).

**Preflight** — expect `absent`:
```sql
SELECT CASE WHEN EXISTS (SELECT 1 FROM information_schema.columns
                          WHERE table_schema='public'
                            AND table_name='score_template_subjects'
                            AND column_name='level_key')
            THEN 'present — skip' ELSE 'absent — apply it' END AS verdict;
```

**Apply** `supabase/migrations/00021_score_template_levels.sql`.

**Verify** — expect two rows, each `6 | 475 | 9.5`:
```sql
SELECT track, count(*) AS subjects, sum(max_score) AS total_marks,
       sum(max_score / 50.0) AS total_coefficient
  FROM public.score_template_subjects
 WHERE scope = 'system' AND level_key = 'upper_secondary' AND grade_number = 12
 GROUP BY track;
```
And the fourteen primary rows from 00016 must be untouched — expect `14`:
```sql
SELECT count(*) FROM public.score_template_subjects
 WHERE scope = 'system' AND level_key IS NULL;
```

**Rollback** In the file. **Read it before running**: it deletes every row with
a non‑null `level_key` and drops `classes.track`, so any class stream you have
set is lost. Harmless today (nothing has set one yet); not harmless later.

**Still safe after the next one?** Yes, with one caveat — if 00024 is applied
and teachers have been assigned to `hs_*` subjects, rolling back 00021 removes
the template rows those assignments name, leaving assignments pointing at
subjects that no longer exist. Roll back 00024 first in that case.

## 00022 — organisation search and join requests

**What** Adds the `join_requests` table with its policies, and three
`SECURITY DEFINER` functions: `search_organisations`, `approve_join_request`,
`reject_join_request`, plus `my_join_requests`.

**Preflight** — expect `absent`:
```sql
SELECT CASE WHEN to_regclass('public.join_requests') IS NULL
            THEN 'absent — apply it' ELSE 'present — skip' END AS verdict;
```

**Apply** `supabase/migrations/00022_organisation_join_requests.sql`.

**Verify** — expect `3` policies and `4` functions:
```sql
SELECT (SELECT count(*) FROM pg_policies
         WHERE schemaname='public' AND tablename='join_requests') AS policies,
       (SELECT count(*) FROM pg_proc p JOIN pg_namespace n ON n.oid=p.pronamespace
         WHERE n.nspname='public'
           AND p.proname IN ('search_organisations','approve_join_request',
                             'reject_join_request','my_join_requests')) AS functions;
```
Confirm there is **no UPDATE policy** on `join_requests` — that absence is
deliberate and is what stops a decision being forged:
```sql
SELECT cmd, count(*) FROM pg_policies
 WHERE schemaname='public' AND tablename='join_requests' GROUP BY cmd;
-- expect SELECT / INSERT / DELETE only. Any UPDATE row is a finding.
```

**Rollback** In the file. `DROP TABLE ... CASCADE` **destroys all join‑request
history**. Structurally reversible; the rows are not.

**Still safe after the next one?** Yes. Independent.

## 00023 — secondary grading schemes

**What** Corrects the two secondary levels' default grading schemes, which
00009 seeded with the primary `/10` ladder, to the `/50` coefficient scheme; and
seeds defaults for any level created since 00009 that has none.

**Preflight** — expect `absent`:
```sql
SELECT CASE WHEN EXISTS (SELECT 1 FROM public.grading_schemes
                          WHERE is_default AND config->>'weighting' = 'coefficient')
            THEN 'present — skip' ELSE 'absent — apply it' END AS verdict;
```

**Apply** `supabase/migrations/00023_secondary_grading_schemes.sql`.

**Verify** — every secondary default should read `50 | coefficient`, every
primary default `10 | simple`:
```sql
SELECT el.name AS level,
       gs.config->>'maxScore'  AS max_score,
       gs.config->>'weighting' AS weighting
  FROM public.grading_schemes gs
  JOIN public.education_levels el ON el.id = gs.education_level_id
 WHERE gs.is_default
 ORDER BY el.name;
```

**Rollback** In the file, in two self-identifying halves: the DELETE finds the
rows this migration inserted by the `seededBy` stamp they carry, and the UPDATE
restores the rows that predate it. **No timestamp, and nothing you need to have
written down.** Either half may be run alone, and running the block twice
changes nothing the second time.

**Still safe after the next one?** Yes. Independent.

**Note** No application code reads these rows at runtime; the score screens
resolve the scheme from `lib/grading/levelSchemes.ts`. This migration makes the
stored rows tell the truth so the admin grading screen stops displaying a
ladder nothing uses. It cannot change a calculated result in either direction.

## 00024 — subject key on teaching assignments

**What** Adds `teacher_assignments.subject_key` so an assignment can name the
subject the score template uses, plus its partial unique index and a class‑first
lookup index.

**Preflight** — expect `absent`:
```sql
SELECT CASE WHEN EXISTS (SELECT 1 FROM information_schema.columns
                          WHERE table_schema='public' AND table_name='teacher_assignments'
                            AND column_name='subject_key')
            THEN 'present — skip' ELSE 'absent — apply it' END AS verdict;
```

**Apply** `supabase/migrations/00024_assignment_subject_key.sql`.

**Verify** — expect the column, both new indexes, and `0` populated rows:
```sql
SELECT (SELECT count(*) FROM pg_indexes
         WHERE tablename='teacher_assignments'
           AND indexname IN ('teacher_assignments_subject_key_uniq',
                             'idx_teacher_assignments_class_subject')) AS new_indexes,
       (SELECT count(*) FROM public.teacher_assignments
         WHERE subject_key IS NOT NULL) AS populated_rows;
-- expect 2 | 0
```

**Rollback** In the file. Dropping the column **loses every subject‑teacher
assignment** made through `/score/collect`. Zero rows today, so harmless now.

**Still safe after the next one?** It is the last one.

## What has and has not been verified

**Verified mechanically.** `node --experimental-strip-types scripts/verify-migrations.mts`
checks all seven files and passes 31/31: every statement is guarded so a second
run is a no-op, every `ON CONFLICT` list matches a real unique index, every
`SECURITY DEFINER` function pins its `search_path`, and every file documents a
rollback. The checker is mutation-tested — remove a guard and it fails.

**Not verified.** None of these has been applied to a Postgres, local or live.
The Docker daemon on this machine does not respond, so no local database could
be started. That means the following remain unproven and are the things to watch
for while applying:

- that each file executes without a syntax or type error;
- that the policies and `SECURITY DEFINER` bodies grant and deny what their
  comments claim;
- that 00023's `UPDATE` matches the rows it is meant to on live data;
- that the seeded Grade-12 rows land against live `education_levels`.

Every migration's **verification query** above exists to close exactly that gap.
Run them. Do not take the static check as evidence a migration worked.

## Point of no return

**Today there is none.** The app is local‑only, so nothing is calling these
functions and every migration above can be rolled back freely.

**That changes the first time you deploy the app.** From that moment:

- **00018/00019 is the hard one.** `createClassAndAssign` in
  `app/onboarding/actions.ts` calls `backfill_teacher_enrolments()` and treats
  failure as fatal — it rolls the new class back rather than leave a v2‑scoped
  account with an empty roster. Drop that function on a live app and **no
  teacher can create a class at all.** Roll it back only with the app stopped.
- **00021, 00022, 00024 degrade rather than break.** The client code was written
  to fall back: a missing template column resolves to the primary curriculum, a
  missing join‑request RPC yields an empty list, a missing `subject_key` column
  resolves every teacher as whole‑class. Rolling these back on a live app
  removes features; it does not take the app down.
- **00020 and 00023** are not read by any calculation. Safe either way.

So the sequence, once you do deploy: **migrations first, verify, app second.**
Never the other way round — the app expects the functions to exist, not the
reverse.
