## ២. ការសម្រេចឈ្មោះ — យក `/classroom` ហើយប្តូរឈ្មោះម៉ូឌុលចាស់

`lib/navigation.ts:215` មានម៉ូឌុល `id: "classroom"` ស្លាក **ថ្នាក់រៀន** រួចហើយ —

ការវាស់វែងបីយ៉ាងធ្វើឲ្យការសម្រេចនេះថោក៖

1. **URL `/classroom` ទំនេរ** — ម៉ូឌុលចាស់ `href` ទៅ `/cleaning-schedule`។
   គ្មានការប៉ះទង្គិច route ទាល់តែសោះ។
2. **`NavModule.id` មិនត្រូវបានរក្សាទុកកន្លែងណាទេ** — វាប្រើតែជា React key,
   ស្ថានភាព active/open (`Sidebar.tsx`, `MobileNav.tsx`, `Breadcrumb.tsx`) និង
   `MOBILE_PRIMARY_IDS`។ គ្មាន localStorage គ្មាន URL គ្មាន database។
3. ឈ្មោះចាស់ជា **ការហៅខុស** តាំងពីដើម។ ការប្តូរវាជាការកែ មិនមែនការសម្របសម្រួល។

| | ចាស់ | ថ្មី |

| ម៉ូឌុលបន្ទប់រៀន | `classroom` · ថ្នាក់រៀន | `facilities` · **បរិក្ខារថ្នាក់** (`/cleaning-schedule`) |
| ម៉ូឌុលថ្នាក់+សិស្ស | — | `classroom` · **ថ្នាក់ និងសិស្ស** (`/classroom`) |

ត្រូវពិនិត្យ `MOBILE_PRIMARY_IDS` (`lib/navigation.ts:328`) ពេលប្តូរ id។

## ៤. ទំព័រថ្មីតែមួយ — `/classroom/classes`

រូបរាងតាមគំរូ trio ធម្មតា (`page.tsx` + `ClassesClient.tsx` + `actions.ts`)។

**អាន៖** `teacher_assignments` របស់អ្នកហៅ (`status='active'`) → `classes` →
`grades` → `academic_years`, បូកនឹងចំនួនសិស្សពី `student_enrollments`
(`.neq('status','withdrawn')` — ច្បាប់ដដែលនឹង roster read ទាំងអស់)។

**កាតមួយក្នុងមួយថ្នាក់៖** ឈ្មោះ · កម្រិត · ឆ្នាំសិក្សា · ស្លាក "គ្រូបន្ទុកថ្នាក់"
· ចំនួនសិស្ស · ប៊ូតុង "ជ្រើសជាថ្នាក់សកម្ម" (សរសេរ `?class=` តាម
`ClassContextSwitcher` ដែលមានស្រាប់ — **កុំបង្កើត switcher ទីពីរ**)។

**បង្កើត៖** ប្រអប់ ៣ វាល ដូចរូបថតទី៥ — ឈ្មោះថ្នាក់ (ចាំបាច់), កម្រិតថ្នាក់,
ឆ្នាំសិក្សា។ វាហៅ **`createClassAndAssign` ដែលមានស្រាប់** ក្នុង
`app/onboarding/actions.ts` — មិនមែន action ថ្មីទេ។ ហេតុផលសំខាន់៖ action នោះ
ហៅ `backfill_teacher_enrolments()` ភ្លាមក្រោយបញ្ចូល assignment ហើយ rollback
ទាំងស្រុងបើ backfill បរាជ័យ។ ការសរសេរផ្លូវបង្កើតថ្នាក់ទីពីរ មានន័យថាផ្លូវមួយ
នឹងភ្លេច backfill ហើយបន្សល់គណនី v2 ដែលមាន roster ទទេ។

> **ចំណាំអំពី backfill លើកទីពីរ៖** 00019 កំណត់ថា backfill ចាប់តែសិស្សដែល
> **គ្មានជួរចុះឈ្មោះទាល់តែសោះ**។ ក្រោយថ្នាក់ទីមួយ សិស្សមានជួររួចហើយ ដូច្នេះ
> ការហៅលើកទីពីរជា no-op។ សុវត្ថិភាព — តែត្រូវ assert វាក្នុង verify script
> ព្រោះនេះជាការសន្មតដែលមើលមិនឃើញពី call site។

**កែ៖** ឈ្មោះថ្នាក់ប៉ុណ្ណោះ។ កម្រិត និងឆ្នាំសិក្សា **មិនកែបានទេ** — ការប្តូរ
ទាំងពីរនោះផ្លាស់ template ដែល resolve បាន និងអត្ថន័យនៃពិន្ទុដែលបញ្ចូលរួច។

**លុប៖ គ្មាន។** មានតែ **archive** (`teacher_assignments.status`)។ ថ្នាក់មួយកាន់
ពិន្ទុ វត្តមាន និងការចុះឈ្មោះ; `DELETE` នឹង cascade បំផ្លាញវាទាំងអស់។ ច្បាប់ដដែល
នឹង §១១ នៃឯកសារពិន្ទុ៖ *ការបង្រួមមិនដែលលុប*។

## ៥. ★ អ្វីដែលត្រូវជួសជុល **មុន** ទំព័រនេះចេញ

`resolveServerScope` (`lib/utils/serverScope.ts:52-69`) ជ្រើសថ្នាក់លំនាំដើមដូច្នេះ៖

```ts
const { data } = await supabase
  .from('teacher_assignments')
  .select(...)
  .eq('teacher_id', userId)
  .eq('status', 'active')          // ← គ្មាន .order()
...
const chosen = requested ?? assignments.find((a) => a.is_homeroom) ?? assignments[0]
```

`createClassAndAssign` សរសេរ `is_homeroom: true` **ជានិច្ច** (`actions.ts:320`),
ហើយ index របស់ 00025 ធានាតែភាពមានតែមួយក្នុង *(teacher, class, year)* —
ដូច្នេះគ្រូម្នាក់អាចមាន **ជួរ homeroom ច្រើន ក្នុងឆ្នាំតែមួយ** ដោយស្របច្បាប់។

សព្វថ្ងៃរឿងនេះមិនកើតឡើងទេ ព្រោះ wizard រត់តែម្តង។ **`/classroom/classes` ធ្វើឲ្យ
វាក្លាយជារឿងធម្មតា** — ហើយពេលនោះ៖

- query គ្មាន `ORDER BY` → Postgres ត្រឡប់ជួរតាមលំដាប់មិនកំណត់,
- `find(is_homeroom)` ចាប់យកជួរណាមួយ,
- **ថ្នាក់លំនាំដើមអាចប្តូរពីសំណើមួយទៅសំណើមួយ** — គ្រូបើក `/score/enter`
  ឃើញថ្នាក់ក, refresh ឃើញថ្នាក់ខ ដោយគ្មានអ្វីប្តូរ។

នេះមិនមែនជាបញ្ហាទ្រឹស្តីទេ៖ វាជាការជ្រើសរើសមិនកំណត់ (nondeterministic) លើ
មុខងារដែលសម្រេចថាពិន្ទុណាត្រូវបានអាន និងសរសេរ។

**ការជួសជុល (Phase ០ នៃ rollout នេះ)** — ពីរផ្នែក, ទាំងពីរតូច៖

1. បន្ថែម `ORDER BY` ដែលកំណត់ច្បាស់លើ query (`is_homeroom DESC, created_at ASC`)
   ដូច្នេះលំដាប់ឈប់អាស្រ័យលើ Postgres។
2. សម្រេចថា "ថ្នាក់លំនាំដើម" មានន័យអ្វីពេលមានច្រើន។ **អនុសាសន៍៖ ថ្នាក់ចាស់ជាងគេ
   ដែលនៅសកម្ម** — ស្ថិរភាព, មិនប្តូរពេលបង្កើតថ្នាក់ថ្មី, ហើយ `?class=` នៅតែ
   គ្របលើវាបាន។

*ជម្រើសមួយទៀតដែលធំជាង៖* បង្ខំ `is_homeroom` ឲ្យមានតែមួយក្នុងមួយឆ្នាំ
(unique index ថ្មី + ជម្រើស "ថ្នាក់ដែលខ្ញុំទទួលបន្ទុក" ក្នុងប្រអប់បង្កើត)។
ត្រឹមត្រូវជាងតាមគំរូអប់រំ តែវាជា migration បូក UI បូកការសម្រេចថាតើគ្រូបឋមដែល

`text-brand-contrast`, `bg-bg-surface`, `border-divider`) ស្ថិតក្នុង

មិនមែនការសរសេរទំព័រឡើងវិញ។** ដូច្នេះច្បាប់សម្រាប់ `/classroom`៖

## ៨. អ្វីដែលក្នុងរូបថត តែ**មិន**ក្នុងវិសាលភាពនេះ

រាយទុកដើម្បីកុំឲ្យអ្នកអានក្រោយគិតថាភ្លេច៖

- **សាខាក្រុមប្រឹក្សាកុមារ** (កាតទី៤) — គណៈកម្មាធិការថ្នាក់, វេនប្រចាំសប្តាហ៍។
  មុខងារថ្មីទាំងស្រុង គ្មានតារាងទ្រទ្រង់។ សមនឹងជាឯកសាររចនាដោយឡែក។
- **បញ្ជីជំហាន ០/៥ លើ dashboard** (រូបថតទី២) — onboarding checklist។ KruSmart
  មាន `onboardingRedirect` រួច ដែលដោះស្រាយបញ្ហាដដែលដោយវិធីផ្សេង (redirect
  ជំនួស checklist)។ ការមានទាំងពីរ ត្រូវការការសម្រេចផលិតផលជាមុន។
- **តំណបញ្ជូនបន្ត / រង្វាន់ ២,០០០៛** — កម្មវិធីទីផ្សារ មិនមែនការគ្រប់គ្រងថ្នាក់។
- **គម្រោង GEIP** — មិនស្គាល់ក្នុង repo នេះ។
